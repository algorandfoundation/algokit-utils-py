Deploying and calling a [smart contract application](https://dev.algorand.co/concepts/smart-contracts/overview/) with AlgoKit Utils starts from one artifact: the application specification (app spec), the JSON document that smart contract frameworks such as Algorand Python and Algorand TypeScript emit when compiling a contract. The format is standardized by [ARC-56](https://dev.algorand.co/arc-standards/arc-0056/). The app spec describes the contract's Application Binary Interface (ABI) methods, its state schema, and its [TEAL](https://dev.algorand.co/concepts/smart-contracts/avm/) programs — everything the library needs to encode calls, compile and deploy the contract, and decode its state and errors.

:::note
Everywhere this page passes an app spec, the older [ARC-32](https://dev.algorand.co/arc-standards/arc-0032/) format is also accepted and converted to ARC-56 internally.
:::

Two classes consume the app spec. `AppFactory` covers everything before a specific app instance exists: creating apps, deploying them idempotently, and handing out clients for them. `AppClient` covers one deployed instance: calling its methods, reading its state, and funding its account. Use the factory when you don't yet know the application ID; use the client when you do. In application code, you'll usually drive both through a generated typed client, which is where this page starts.

## Use Typed Clients

For contracts you own, the recommended way to deploy and call an app is a _typed_ client, generated from the app spec with [AlgoKit CLI](https://github.com/algorandfoundation/algokit-cli/blob/main/docs/features/generate.md#1-typed-clients):

```bash
algokit generate client HelloWorld.arc56.json --output hello_world_client.py
```

The command writes a module containing a typed factory and a typed client named after your contract — here `HelloWorldFactory` and `HelloWorldClient`. These classes wrap `AppFactory` and `AppClient`, so everything on this page applies to them: deployment, state access, and error handling all work the same. The difference is that each ABI method becomes a typed Python method, with arguments and return values checked against the contract:

```python
from algokit_utils import AlgorandClient, OnSchemaBreak, OnUpdate
from smart_contracts.artifacts.hello_world.hello_world_client import (
    HelloArgs,
    HelloWorldClient,
    HelloWorldFactory,
)

# Connect to the network and resolve the deployer account
algorand = AlgorandClient.from_environment()
deployer = algorand.account.from_environment("DEPLOYER")

# Get a typed factory
factory = algorand.client.get_typed_app_factory(
    HelloWorldFactory, default_sender=deployer.address
)

# Deploy idempotently; AppendApp deploys a fresh app when the contract changes
app_client, result = factory.deploy(
    on_update=OnUpdate.AppendApp,
    on_schema_break=OnSchemaBreak.AppendApp,
)

# Call an ABI method through the typed client
response = app_client.send.hello(args=HelloArgs(name="world"))
print(response.abi_return)  # Hello, world
```

The `deploy()` call is the same idempotent deployment covered under [Deploy an App](#deploy-an-app) below, and `result` carries the same deployment result. The difference shows in the last line: `hello` takes typed arguments, and `response.abi_return` is already decoded to the method's declared return type.

When the app is already deployed, skip the factory and construct the typed client directly from its application ID:

```python
app_client = algorand.client.get_typed_app_client_by_id(
    HelloWorldClient, app_id=1234, default_sender=deployer.address
)
```

`get_typed_app_client_by_creator_and_name` and `get_typed_app_client_by_network` cover the same resolution modes as the untyped lookups described under [Get an App Client](#get-an-app-client) below.

### Fill In Template Variables

Contracts can defer constants to deployment time: a `TemplateVar` in Algorand Python or Algorand TypeScript becomes a `TMPL_{NAME}` placeholder in the app spec's TEAL. Fill the placeholders through `compilation_params` when `deploy()` compiles the programs:

- `deploy_time_params` maps each placeholder name, without the `TMPL_` prefix, to an integer, string, or bytes value.
- `updatable` and `deletable` fill the reserved `TMPL_UPDATABLE` and `TMPL_DELETABLE` placeholders, fixing at deploy time whether the app can ever be updated or deleted.

The remaining examples on this page use a `State` test contract that declares a `TMPL_VALUE` constant alongside the update and delete gates; deploying it fills in all three:

### Bare Create

In some cases it may be necessary to bypass the managed `deploy()` flow and create an app unconditionally. The factory's send surface sends a plain creation transaction, making a new app on every call, and returns a client for it:

```python
new_client, create_result = factory.send.bare.create()
```

`factory.send.create(AppFactoryCreateMethodCallParams(method="create_abi", args=[...]))` is the equivalent for contracts with an ABI create method. Apps created this way carry no deployment metadata, so `deploy()` will not find them.

### Redeploy Safely

Running `deploy()` again is safe: it finds the app already deployed under the same name for the creator account, compares its on-chain programs and schema against the new compilation, and acts on what changed through two parameters:

| Parameter         | Governs                                                                |
| ----------------- | ---------------------------------------------------------------------- |
| `on_update`       | Changed program code                                                   |
| `on_schema_break` | A schema grown beyond the global or local state reserved at creation   |

Each parameter chooses an action. Both default to `Fail`, and because the schema reservation is fixed at creation, `UpdateApp` is available only to `on_update`:

| Action       | What happens                                           |
| ------------ | ------------------------------------------------------ |
| `Fail`       | Stop the deployment                                    |
| `UpdateApp`  | Update the app in place                                |
| `ReplaceApp` | Delete the existing app and create a new one           |
| `AppendApp`  | Create a new app and leave the existing one untouched  |

Redeploying unchanged code performs no transactions at all. Here a changed template value turns the second deploy into an in-place update:

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/applications.py"
  snippet="REDEPLOY_APP"
  lang="py"

/>

The result's `operation_performed` reports which path was taken — `Create`, `Update`, `Replace`, or `Nothing` — and carries the corresponding transaction results.

To find the deployed app, `deploy()` reads deployment metadata that the library records in an [ARC-2](https://dev.algorand.co/arc-standards/arc-0002/) transaction note. The lookup works the same on every network, so a single deployment script serves LocalNet, TestNet, and MainNet. It requires an indexer client on the `AlgorandClient`, unless a pre-fetched lookup is passed as `existing_deployments`, and results are cached per creator account. The name is the app's entire identity: a different contract deployed under the same name by the same creator is treated as a code change to the existing app, not as a new app.

When the app is already deployed, construct a client for it directly:

  lang="py"

An app can also be resolved by its creator and name, using the same lookup as `deploy()`, or from a factory, which pre-populates the app spec, default sender, and compilation source maps:

```python
app_client = algorand.client.get_app_client_by_creator_and_name(
    creator_address=deployer.address,
    app_name="State",
    app_spec=app_spec,
)
app_client = factory.get_app_client_by_id(app_id=1234)
```

An app spec can also embed the IDs of its published deployments in a `networks` map, keyed by network. When the spec records an ID for the connected network, `algorand.client.get_app_client_by_network(app_spec=app_spec)` returns a client without needing an app ID.

## Call the App

`AppClientMethodCallParams` names an ABI method and passes arguments as plain Python values. The client encodes them per the app spec, sends the call, and decodes the return value into `abi_return`:

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/applications.py"
  snippet="CALL_APP_METHOD"
  lang="py"
  frame="none"
/>

The client's `send` surface covers every kind of call:

- `send.call()` makes a no-op call.
- `send.opt_in()`, `send.close_out()`, `send.update()`, and `send.delete()` send the same shape of method call with a different on-complete action. Update recompiles the programs, so it accepts the same `compilation_params` as deploy.
- `send.bare.*` covers bare calls that invoke no ABI method.

Alongside `send`, the client mirrors the `AlgorandClient` surface with `app_client.params.*` and `app_client.create_transaction.*` for composing calls into transaction groups without sending them.

### Readonly Methods

An app spec can declare a method `readonly`. The client never submits a transaction for these methods: they run through algod's simulate endpoint, returning their result immediately without paying a fee or writing to the ledger. Methods without the flag are signed, submitted, and confirmed like any other transaction. The calling code is identical either way.

## Read State

An ARC-56 app spec declares the app's state — keys and maps in global, local, and box storage, with their value types — so the client can read storage and decode it into Python values. Each storage kind exposes the same accessors: `get_all()`, `get_value(name)`, `get_map_value(map_name, key)`, and `get_map(map_name)`. The last returns a whole map as a dict keyed by the string form of each decoded key.

## Handle Logic Errors

When a smart contract call fails, algod reports a `logic eval error` identifying only a program counter position. ## Under the Hood

The factory and client build on lower-level interfaces on `AlgorandClient` that remain available when there is no app spec — for example when working with hand-written TEAL:

- [`algorand.app_deployer`](/algokit-utils-py/api/algokit_utils/applications/app_deployer/) provides the idempotent, name-resolved deployment described under [Redeploy Safely](#redeploy-safely) for raw create, update, and delete params. `factory.deploy()` delegates to it.
- [`algorand.send.app_create()`](/algokit-utils-py/api/algokit_utils/transactions/transaction_sender/) and its siblings send individual application transactions, as bare calls or as `*_method_call` ABI variants.
- `algorand.app`, the [`AppManager`](/algokit-utils-py/api/algokit_utils/applications/app_manager/), compiles TEAL and caches each result with its source map, substitutes template variables, and reads and decodes app information, state, and boxes.
