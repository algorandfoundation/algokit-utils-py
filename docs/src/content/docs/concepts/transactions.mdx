Every action on Algorand — moving Algo, creating an asset, calling a smart contract — is a [transaction](https://dev.algorand.co/concepts/transactions/types/): a signed, atomic instruction the network validates and records. AlgoKit Utils constructs, signs, and submits all of them through one consistent model, so the shape you learn for a payment carries over to every other type.

This page covers how the library builds, signs, and sends transactions and configures the fields they share: sending payments, registering consensus keys, controlling fees, leases, multisig authorization, atomic groups and simulation, building unsigned transactions, structured notes, per-send options, and rekeying. Constructing assets and application calls follows the same model and is covered on their own pages. For the protocol-level definition of each transaction type and its wire format, see the Algorand developer portal.

Building and sending is only half the story; for interpreting what a send returns — confirmations, transaction IDs, and ABI return values — see [Transaction management](/algokit-utils-py/concepts/core/transaction/), which documents the result types every send method returns.

## The Transaction Model

Every transaction starts as a _params dataclass_ — `PaymentParams`, `AssetTransferParams`, `OnlineKeyRegistrationParams`, and so on. You fill in the fields for the operation, then hand the params to one of three interfaces on [`AlgorandClient`](/algokit-utils-py/concepts/algorand-client/) depending on what you want back:

| Interface                              | Use when you want to                                            |
| -------------------------------------- | --------------------------------------------------------------- |
| `algorand.send.<type>(params)`         | Build, sign, submit, and wait for confirmation in one call      |
| `algorand.create_transaction.<type>(params)` | Build the unsigned transaction and handle signing/sending yourself |
| `algorand.new_group().add_<type>(params)`    | Collect several transactions into one atomic group              |

Signing is automatic: the client resolves each transaction's sender to its registered signer, so you rarely pass a signer explicitly. Suggested parameters (the fee, current round, and genesis identifiers) are fetched and cached for you. Both are covered under [Algorand Client](/algokit-utils-py/concepts/algorand-client/) and apply to everything below.

Every params dataclass shares a common set of fields in addition to its type-specific ones:

| Common field                                       | Purpose                                                             |
| -------------------------------------------------- | ------------------------------------------------------------------- |
| `sender`                                           | The account authorizing and paying for the transaction             |
| `signer`                                           | An explicit signer, overriding the registered one                  |
| `note`                                             | Arbitrary bytes recorded with the transaction                      |
| `lease`                                            | A mutual-exclusion lock (see [Leases](#reserve-exclusivity-with-a-lease)) |
| `static_fee` / `extra_fee` / `max_fee`             | Fee control (see [Fees](#control-fees))                            |
| `validity_window` / `first_valid_round` / `last_valid_round` | The round range in which the transaction is valid       |
| `rekey_to`                                          | Rekey the sender to a new authorizing address                     |

## Control Fees

Algorand's minimum fee is 1000 microAlgo, and the client applies it by default — you don't set a fee to send a normal transaction. Three fields adjust that behavior when you need to:

| Field        | Effect                                                                             |
| ------------ | ---------------------------------------------------------------------------------- |
| `static_fee` | Sets an exact, fixed fee, overriding the calculated one                            |
| `extra_fee`  | Adds an amount on top of the calculated minimum (e.g. to cover a fee in a group)   |
| `max_fee`    | Caps the fee the client will accept; sending raises if the fee would exceed it     |

`static_fee` pins the fee to an exact value:

`max_fee` is a safety bound rather than a fee: the transaction pays its normal fee, but sending fails fast if that fee ever exceeds the cap.

### Pool Fees Across a Group

Algorand charges fees per group, not per transaction: the network only requires the group's total fee to cover every transaction in it. So one transaction can pay extra to cover another that pays nothing. Here the second payment covers both fees and the first pays zero — the pattern a sponsor uses to pay a user's transaction fee:

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/transactions.py"
  snippet="FEE_POOLING"
  lang="py"
  frame="none"
/>

The same mechanism covers the fees of inner transactions issued by a smart contract call, so the outer caller pays for them. AlgoKit Utils can compute that coverage automatically with the `cover_app_call_inner_transaction_fees` send option — see [Transaction Composer](/algokit-utils-py/concepts/advanced/transaction-composer/) for the details.

## Reserve Exclusivity with a Lease

A lease is a 32-byte value that locks the `(sender, lease)` pair until the transaction's last-valid round. While the lock holds, no second transaction with the same pair can be confirmed — useful for guaranteeing a recurring or replaceable payment runs at most once per window.

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/transactions.py"
  snippet="LEASE"
  lang="py"
  frame="none"
/>

Changing either the sender or the lease value creates a new, independent lock. Once the validity window passes, the lease is released.

## Send from a Multisig Account

A [multisig account](https://dev.algorand.co/concepts/accounts/multisig/) requires signatures from a threshold of its member accounts before the network accepts a transaction from it. In AlgoKit Utils you send from a multisig exactly as from any other account — the difference is entirely in how the account and its signer are set up.

Create the account with `algorand.account.multisig`, passing a `MultisigMetadata` (the version, the signing threshold, and every member address) and the member accounts that will sign. This registers a signer for the multisig address, so sending a transaction from it is signed by those members automatically — no explicit `signer` needed:

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/transactions.py"
  snippet="MULTISIG"
  lang="py"
  frame="none"
/>

`addresses` lists every member and defines the multisig address (order matters); `signing_accounts` is the subset present to sign now, and must cover the threshold. Because the signer is built when the account is created, all required members must be available at that point — for coordinating signatures across parties or processes, sign at the transaction level instead.

## Sign with a Logic Signature

A [logic signature](https://dev.algorand.co/concepts/smart-contracts/logic-sigs/) authorizes a transaction with a compiled program instead of a private key: the program runs at submission and the transaction is valid only if it approves. Create one with `algorand.account.logicsig`, passing the compiled program bytes (here produced from TEAL with `algorand.app.compile_teal`). As with multisig, this registers a signer for the logic signature's address, so sending from it is authorized automatically:

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/transactions.py"
  snippet="LOGICSIG"
  lang="py"
  frame="none"
/>

:::caution
The `int 1` program above approves _every_ transaction, so anyone can spend the escrow. It is illustrative only — a real logic signature encodes the exact conditions under which it will approve.
:::

The address above is a _contract account_ (an escrow whose address is the program's hash), so the program authorizes spending from itself. A logic signature can also be _delegated_ — an account grants the program authority to sign on its behalf — in which case the program signs for that account's transactions. Either way the account exposes a `signer`, so you can also attach it explicitly to any transaction's `signer` field.

## Build Unsigned Transactions

`algorand.send.<type>` builds, signs, and submits in one step. When you need control over signing or submission — to hand a transaction to a wallet, sign it out of band, or submit it yourself — `algorand.create_transaction.<type>` returns the unsigned `algosdk` transaction instead. You then sign and submit it through the SDK client:

The transaction the client builds is a standard `algosdk` transaction, so anything the SDK can do with it applies. To collect several such transactions into an atomic group, add them with [`add_transaction`](#group-and-simulate-transactions).

## Attach a Structured Note (ARC-2)

Every transaction carries an optional `note` of arbitrary bytes. [ARC-2](https://dev.algorand.co/arc-standards/arc-0002/) standardizes that field so on-chain tools can recognize which application wrote a note and in what format, encoding it as `<dapp_name>:<format><data>`. `TransactionComposer.arc2_note` builds a conforming note; pass the bytes it returns as the `note` field on any transaction:

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/transactions.py"
  snippet="ARC2_NOTE"
  lang="py"
  frame="none"
/>

The `format` is one of `m` (MsgPack), `b` (raw bytes), `u` (UTF-8), or `j` (JSON); `dapp_name` must be 5–32 characters. See the [ARC-2 specification](https://dev.algorand.co/arc-standards/arc-0002/) for the full convention.

## Send Parameters

The params dataclass describes _what_ the transaction is; a separate `send_params` argument controls _how_ it is sent. Pass it as the second argument to any `algorand.send.<type>` call or to a group's `send()`:

| Option                                    | Effect                                                                          |
| ----------------------------------------- | ------------------------------------------------------------------------------- |
| `max_rounds_to_wait`                      | How many rounds to wait for confirmation before giving up                       |
| `suppress_log`                            | Suppress the library's send and confirmation logging                            |
| `populate_app_call_resources`             | Auto-populate the resources an app call references (see [Applications](/algokit-utils-py/concepts/applications/)) |
| `cover_app_call_inner_transaction_fees`   | Have the caller cover inner-transaction fees (see [Transaction Composer](/algokit-utils-py/concepts/advanced/transaction-composer/)) |

## Rekey an Account

Rekeying moves the authority to sign for an account to a different address while keeping the account's own address unchanged. Every params dataclass exposes a `rekey_to` field that rekeys the sender as a side effect of the transaction, and `algorand.account.rekey_account(...)` is a dedicated helper for doing it on its own. Because a rekey can permanently transfer control of an account, the mechanics, the risks, and how to sign for a rekeyed sender afterward are covered with the account model.

## Other Transaction Types

Payments and key registrations are constructed directly on this page; the remaining types are covered where they belong:

- **Asset transactions** — creating, configuring, transferring, freezing, and opting in and out of Algorand Standard Assets. These use the same params-and-send model through `algorand.send.asset_*`.
- **Application calls** — calling, creating, updating, and deleting smart contracts, including ABI method calls. These are driven through app clients rather than raw params.

State Proof and Heartbeat transactions also exist at the protocol level, but they are generated by the network rather than constructed by application code, so the library does not build them.
