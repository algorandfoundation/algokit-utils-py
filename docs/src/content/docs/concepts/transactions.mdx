Moving Algo, creating an asset, or calling a smart contract all happen the same way on Algorand: as a [transaction](https://dev.algorand.co/concepts/transactions/types/), a signed instruction the network validates and records atomically. AlgoKit Utils builds every one of them through a single model. Learn the shape for a payment and it carries over to every other type.

That one model covers most of what you will do: payments, consensus key registration, fee control, leases, multisig and logic-signature authorization, atomic groups, and simulation. Each has a section below. Assets and application calls work the same way, on their own pages. For the protocol-level definition of each transaction type and its wire format, see the Algorand developer portal.

To read what a send returns, such as confirmations, transaction IDs, and ABI return values, see [Transaction management](/algokit-utils-py/concepts/core/transaction/). It documents the result type every send method returns.

## The Transaction Model

Every transaction starts as a _params dataclass_: `PaymentParams`, `AssetTransferParams`, `OnlineKeyRegistrationParams`, and so on. Fill in the fields for the operation, then hand the params to one of three interfaces on [`AlgorandClient`](/algokit-utils-py/concepts/algorand-client/). Which one you pick depends on what you want back:

| Interface                              | Use when you want to                                            |
| -------------------------------------- | --------------------------------------------------------------- |
| `algorand.send.<type>(params)`         | Build, sign, submit, and wait for confirmation in one call      |
| `algorand.create_transaction.<type>(params)` | Build the unsigned transaction and handle signing/sending yourself |
| `algorand.new_group().add_<type>(params)`    | Collect several transactions into one atomic group              |

The client resolves each transaction's sender to its registered signer, so you rarely pass a signer explicitly. When you do, the `signer` field accepts any account wrapper the library provides (including the multisig and logic-signature accounts below) or a raw `algosdk` transaction signer. Suggested parameters (the fee, current round, and genesis identifiers) are fetched and cached for you. Both are covered under [Algorand Client](/algokit-utils-py/concepts/algorand-client/) and apply to everything below.

Every params dataclass also carries a set of common fields, in addition to its type-specific ones:

| Common field                                       | Purpose                                                             |
| -------------------------------------------------- | ------------------------------------------------------------------- |
| `sender`                                           | The account authorizing and paying for the transaction             |
| `signer`                                           | An explicit signer, overriding the registered one                  |
| `note`                                             | Arbitrary bytes recorded with the transaction                      |
| `lease`                                            | A mutual-exclusion lock (see [Leases](#reserve-exclusivity-with-a-lease)) |
| `static_fee` / `extra_fee` / `max_fee`             | Fee control (see [Fees](#control-fees))                            |
| `validity_window` / `first_valid_round` / `last_valid_round` | The round range in which the transaction is valid       |
| `rekey_to`                                          | Rekey the sender to a new authorizing address                     |

## Control Fees

Algorand's minimum fee is 1000 microAlgo, and the client applies it by default. A normal transaction needs no fee field at all. Three fields adjust that when you need them:

| Field        | Effect                                                                             |
| ------------ | ---------------------------------------------------------------------------------- |
| `static_fee` | Sets an exact, fixed fee, overriding the calculated one                            |
| `extra_fee`  | Adds to the calculated fee (e.g. to cover another transaction's fee in a group)    |
| `max_fee`    | Caps the fee the client will accept; sending raises if the fee would exceed it     |

`static_fee` pins the fee to an exact value:

/>

`extra_fee` adds to the fee the client already calculated rather than replacing it. Use it when one transaction has to pay more than its own share, such as covering the fee of an inner transaction an app call will issue:

### Pool Fees Across a Group

Algorand charges fees per group, not per transaction. The network only checks that the group's total covers every transaction in it. So one transaction can pay extra and cover another that pays nothing. In the example below the second payment pays both fees and the first pays zero. This is how a sponsor covers a user's transaction fee:

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/transactions.py"

/>

The same mechanism covers the fees of inner transactions issued by a smart contract call, so the outer caller pays for them. AlgoKit Utils can compute that coverage for you through the `cover_app_call_inner_transaction_fees` send option. See [Transaction Composer](/algokit-utils-py/concepts/advanced/transaction-composer/) for the details.

## Reserve Exclusivity with a Lease

A lease is a value of up to 32 bytes that locks the `(sender, lease)` pair until the transaction's last-valid round. A shorter value is padded to 32 bytes. While the lock holds, no second transaction with the same pair can confirm. That guarantees a recurring or replaceable payment runs at most once per window.

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/transactions.py"
  snippet="LEASE"
  lang="py"
  frame="none"
/>

Changing either the sender or the lease value creates a new, independent lock. Once the validity window passes, the lease is released.

## Send from a Multisig Account

A [multisig account](https://dev.algorand.co/concepts/accounts/multisig/) needs signatures from a threshold of its members before the network will accept a transaction from it. You send from one exactly as from any other account. The only difference is in how you set up the account and its signer.

Create the account with `algorand.account.multisig`, passing a `MultisigMetadata` (the version, the signing threshold, and every member address) and the member accounts that will sign. This registers a signer for the multisig address. A transaction sent from that address is then signed by those members automatically, with no explicit `signer`:

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/transactions.py"
  snippet="MULTISIG"
  lang="py"
  frame="none"
/>

`addresses` lists every member and sets the multisig address, so order matters. `signing_accounts` is the subset present to sign right now, and it must cover the threshold. The signer is built when the account is created, so every required member has to be available at that point. To coordinate signatures across separate parties or processes, sign at the transaction level instead.

## Sign with a Logic Signature

A [logic signature](https://dev.algorand.co/concepts/smart-contracts/logic-sigs/) authorizes a transaction with a compiled program instead of a private key. The program runs at submission, and the transaction is valid only if it approves. Create one with `algorand.account.logicsig`, passing the compiled program bytes (here produced from TEAL with `algorand.app.compile_teal`). As with multisig, this registers a signer for the logic signature's address, so sending from it is authorized automatically:

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/transactions.py"
  snippet="LOGICSIG"
  lang="py"
  frame="none"
/>

:::caution
The `int 1` program above approves every transaction, so anyone can spend the escrow. It is illustrative only. A real logic signature encodes the exact conditions under which it approves.
:::

The address above is a _contract account_: an escrow whose address is the program's hash, so the program authorizes spending from itself. A logic signature can also be _delegated_, where an account grants the program authority to sign on its behalf. In that case the program signs for that account's transactions. Either way the account exposes a `signer`, so you can attach it explicitly to any transaction's `signer` field.

## Build Unsigned Transactions

`algorand.send.<type>` constructs the transaction and takes it all the way through signing and submission. Sometimes you want to stop before that: to hand the transaction to a wallet, sign it out of band, or submit it yourself. `algorand.create_transaction.<type>` returns the unsigned `algosdk` transaction instead. You sign and submit it through the SDK client:

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/transactions.py"
  snippet="BUILD_UNSIGNED"
  lang="py"
  frame="none"
/>

The transaction the client builds is a standard `algosdk` transaction, so anything the SDK can do with it applies. To collect several such transactions into an atomic group, add them with [`add_transaction`](#group-and-simulate-transactions). Building an ABI method call is different: those `create_transaction` methods return a set of built transactions rather than a single one, and are covered under [Applications](/algokit-utils-py/concepts/applications/).

## Attach a Structured Note (ARC-2)

Every transaction carries an optional `note` of arbitrary bytes. [ARC-2](https://dev.algorand.co/arc-standards/arc-0002/) gives that field a convention, `<dapp_name>:<format><data>`, so on-chain tools can tell which application wrote a note and in what format. `TransactionComposer.arc2_note` builds a conforming note. Pass the bytes it returns as the `note` field on any transaction:

<RemoteCode
  src="https://raw.githubusercontent.com/algorandfoundation/algokit-utils-py/refs/heads/main/examples/concepts/transactions.py"
  snippet="ARC2_NOTE"
  lang="py"
  frame="none"
/>

The `format` is `m` for MsgPack, `b` for raw bytes, `u` for UTF-8, or `j` for JSON. The `dapp_name` must be 5 to 32 characters and start with a letter or digit. See the [ARC-2 specification](https://dev.algorand.co/arc-standards/arc-0002/) for the full convention.

## Send Parameters

The params dataclass describes the transaction itself. A separate `send_params` argument controls how it is sent. Pass it as the second argument to any `algorand.send.<type>` call or to a group's `send()`:

| Option                                    | Effect                                                                          |
| ----------------------------------------- | ------------------------------------------------------------------------------- |
| `max_rounds_to_wait`                      | How many rounds to wait for confirmation before giving up                       |
| `suppress_log`                            | Suppress the library's send and confirmation logging                            |
| `populate_app_call_resources`             | Auto-populate the resources an app call references (see [Applications](/algokit-utils-py/concepts/applications/)) |
| `cover_app_call_inner_transaction_fees`   | Have the caller cover inner-transaction fees (see [Transaction Composer](/algokit-utils-py/concepts/advanced/transaction-composer/)) |

## Rekey an Account

Rekeying moves the authority to sign for an account to a different address, while the account's own address stays the same. Every params dataclass has a `rekey_to` field that rekeys the sender as a side effect of the transaction. `algorand.account.rekey_account(...)` does it on its own. A rekey can permanently hand control of an account to another key, so the mechanics, the risks, and how to sign for a rekeyed sender afterward live with the account model.

## Other Transaction Types

Payments and key registrations are built directly on this page. Two other library-built types live on their own pages:

- **Asset transactions.** Creating, configuring, transferring, freezing, and opting in and out of Algorand Standard Assets. Same params-and-send model, through `algorand.send.asset_*`.
- **Application calls.** Calling, creating, updating, and deleting smart contracts, including ABI method calls. These go through app clients rather than raw params.

State Proof and Heartbeat transactions exist at the protocol level too, but the network generates them rather than application code, so the library does not build them.
